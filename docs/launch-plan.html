From here to five hundred

The software is finished. Everything between now and a real user base is deployment, distribution, and three gaps nobody has written down yet. Each phase below has one exit condition — a thing that has to be true before the next phase is worth starting.

5 phases 3 untracked gaps 2 hard gates software: done
Before the plan

What "500 users" has to mean

The number needs pinning down or the plan is unfalsifiable, because these are three wildly different businesses:

ReadingDifficultyWhat it actually proves
500 waitlist emails weeks You can reach people. Says nothing about whether they'd pay.
500 registered accounts months People will invest a click. Still not a business.
500 paying buyers a year+ A real company. At $99–149 a sale that's roughly $60k of volume.

This plan targets 500 registered accounts with a meaningful fraction having bought. The honest sequencing point: the project's actual question — does demo-before-pay plus a refund button change whether people buy? — gets answered at ten users, not five hundred. Phase 3 is where the real risk sits. Everything after it is scaling something already known to work, and there is no point scaling something that doesn't.

Newly found

Three gaps not on any existing roadmap

These turned up auditing the code against this goal. None are on the current roadmap, and all three are load-bearing before real strangers arrive.

  • There is no notification system whatsoever. Not email, not in-app. A seller makes a sale and is never told. A buyer refunds and nobody hears. A marketplace where the seller learns about their own sale by refreshing a dashboard does not function.
  • There is no analytics. You cannot count 500 users, and more importantly you cannot see whether people click the demo — which is the one number the entire thesis rests on.
  • There is no moderation path. A seller sets their own listing to live; the pending_review status exists but nothing consumes it. Fine with three listings that are all yours. Not fine the first time a stranger lists something.
1

Get it on the internet

This week · blocked by nothing
Rigel + Jack

A public URL a stranger can open, use a demo on, and leave an email at. This does not wait on Stripe — the landing page makes zero /api/ calls, so payments being in review blocks nothing here.

  • Code on GitHub, Supabase live, schema verified
  • Security pass complete, 203 assertions passing
  • Install Node (nodejs.org, macOS .pkg, double-click)
  • Deploy: npx wrangler pages deploy .
  • Buy a domain and point it at the Pages project. forkable.dev or similar — a pages.dev URL costs you credibility with the exact audience you want
  • Add analytics. Cloudflare Web Analytics is free, is a single script tag, needs no cookie banner, and adds no build step. Turn it on before traffic arrives, not after
  • Sign up on your own waitlist from your phone; confirm the row in Supabase
Exit: someone who is not you, Jack, or Luke opens the URL, clicks into a working demo, and leaves an email.
2

Make money actually work

Blocked on Stripe review
Rigel

Every line of this is written and unit-tested but has never moved a real cent. Until a purchase and a refund both complete end to end, treat payments as unproven.

  • Stripe Connect platform profile submitted and approved
  • Register the webhook at /api/webhook with exactly three events: checkout.session.completed, charge.refunded, account.updated
  • Fill all 7 values in .dev.vars; run node scripts/preflight.mjs until it says Ready
  • Walk the whole loop locally: two accounts, buy with 4242 4242 4242 4242, then refund
  • Set the same 7 vars in the Cloudflare dashboard and redeploy — environment variables do not apply retroactively to an existing deploy
  • Switch to sk_live_, and set a spend alert first
⚠ Schedule two cron jobs. This is the quietest failure mode in the project. Cloudflare Pages has no cron trigger, so both need an external caller (GitHub Actions, cron-job.org) sending the same CRON_SECRET. Without /api/release-payouts, sellers are never paid and nothing errors — the money simply sits. Without /api/check-demos, broken demos rot silently and the entire pitch dies one listing at a time.
Exit: one real purchase and one real refund, by someone who is not you, with the seller payout landing after the window closes.
3

First ten real users

The phase that actually matters
Rigel + Luke

This is where the thesis is tested. Ten strangers is enough to learn whether demo-before-pay changes anything — and cheap enough that being wrong costs a fortnight instead of a year. Recruit these by hand. Do not automate anything here.

  • Write down, before launching, what would count as failure. If nobody clicks a demo, the product thesis is wrong and no amount of traffic fixes it
  • Post where builders already are: Indie Hackers, r/SideProject, r/webdev, Hacker News Show HN, relevant Discord servers. Lead with the live demo — that is the pitch
  • Message people directly. Ten conversations beats one broadcast at this stage
  • Watch demo click-through above everything else. Visits are vanity; the demo click is the thesis
  • Talk to everyone who signs up and does not buy. That is the most valuable conversation available to you right now
Exit: ten strangers used a demo, and at least one bought without you asking them to.
4

Let other people sell

Hard security gate — do not shortcut
Jack

Three listings from one seller is not a marketplace. But opening supply is the moment the security model stops being theoretical, because strangers start supplying the strings your site renders and embeds.

⚠ Set demoOrigin before accepting a single third-party demo. Demos currently run from the app's own origin, which is only safe because every one is your code. An iframe with allow-same-origin that is also same-origin with the page can reach into it. Serve demos/ as a second Cloudflare Pages project and set demoOrigin in config.js — that makes first-party demos cross-origin like everyone else's, and the browser enforces the boundary instead of us. This is not optional and it is not a later problem.
  • Second Pages project serving demos/; set demoOrigin; confirm the first-party demos still load
  • Build notifications. Minimum: seller emailed on a sale, buyer emailed on purchase and on refund. A Pages Function calling Resend over plain fetch keeps the no-build-step rule intact
  • Give yourself a moderation path. It can start as a saved SQL query plus the ability to set status = 'delisted'. What matters is that you can take something down within minutes, not that it is pretty
  • Write the seller rules down publicly: what may be listed, what the demo must do, when you will delist
  • Recruit 3–5 sellers by hand, the same way as the first ten users
Exit: a seller who is not you has listed a tool, passed review, and made a sale.
5

Scale to five hundred

Only once phases 3 and 4 have cleared
All three

Everything to this point was learning whether the thing works. This phase is repetition of whatever channel worked in phase 3 — and the honest answer is that you will not know which channel that is until you are there.

  • Double down on the one channel that worked. Resist adding a second until the first is genuinely saturated
  • Use the request board as the demand engine. Buyers posting what they'd pay for is the cheapest market research that exists, and it gives new sellers a reason to show up: visible demand with a price attached
  • Make each listing its own shareable page with real preview images — the unit of distribution is a tool, not the homepage
  • Publish the JSON and RSS feeds you already built. Newsletters and aggregators consume those without you doing anything
  • Watch what breaks: the unauthenticated GitHub API in /api/import-repo caps out around 30 imports an hour across all users; demo health checks are capped at 200 listings a run; the feed returns 50 items with no pagination
  • Revisit Stage 4 only when the request board tells you which part people actually want
Exit: 500 registered accounts, a meaningful fraction having bought, and a repeatable channel you understand.
Still deferred

What we are deliberately not building

Unchanged from the existing roadmap, and worth restating because with three people the temptation to build multiplies: the fork-and-deploy manifest and wizard, sandbox automation, a polished admin UI, multi-currency, per-buyer refund limits.

They are not missing by accident. Every week on that list is a week not spent finding out whether anyone buys. Read the request board first — it will tell you which of these is actually wanted, and the answer is rarely the one that was most fun to imagine.

Phase 1 is the only one with nothing in front of it. Everything else is either gated on Stripe's review queue, on ten strangers telling you something true, or on a security boundary that has to exist before strangers can supply content. Start there.
