Findings

What was actually wrong

Every listing's repo URL was readable by anyone

Fixed
supabase/schema.sql · supabase/payments.sql · scripts/preflight.mjs

The SQL hid sensitive columns with revoke select (repo_url) …. That statement runs clean and does nothing: a table-level grant implies every column, and a column revoke cannot subtract from it. Supabase hands new tables exactly that grant. So on a fresh install, the thing you are selling was free to read — along with every seller's Stripe Connect ID.

This is scar #5 reopened. The original diagnosis was right and the remedy was wrong, and nothing caught it because the remedy was never run against a database. preflight.mjs detected the leak correctly but printed that same broken one-liner as the cure — so following its advice gave you a clean run and an unchanged leak.

Nine ways to write an address the SSRF filter didn't recognise

Fixed
functions/api/check-demo.js → functions/_shared/net-safety.js

The filter matched a dotted-quad pattern. A hostname does not have to be dotted-quad to resolve, so these all sailed through to a server sitting inside Cloudflare's network: 

2130706433              → 127.0.0.1   (32-bit decimal)
0x7f000001              → 127.0.0.1   (hex)
0177.0.0.1              → 127.0.0.1   (octal)
127.1                   → 127.0.0.1   (short form)
::ffff:169.254.169.254  → cloud metadata service

Worse, the fetch used redirect: 'follow' — so even a correct filter was decorative. A perfectly public URL that redirects to 169.254.169.254 passed the check and was followed anyway. Redirects are now resolved by hand with every hop re-checked.

The hourly demo checker had no address filter at all

Fixed
functions/api/check-demos.js

The cron sweep fetched demo_url straight off live listings with only a protocol check. And it wasn't blind: the HTTP status and error text land in sandbox_instances, which that seller can read back through their own listing. A seller could point a demo at an internal address and read the answer.

One seller's title could take down the whole RSS feed

Fixed
functions/api/feed.js

The feed escaped < > & ' " but not control characters. Postgres stores a vertical tab happily; XML forbids it outright and has no escape for it. One listing carrying one such byte makes the entire feed unparseable for every subscriber — with no error anywhere on your side.

The local-rules suite passed on its first run — the mock had not drifted. That's the good outcome, and it can't drift silently from here. It did surface one real gap: local mode applied no CHECK constraints, so it accepted a negative price and an "unlimited clients" tier priced below the single-client one. Postgres refuses both. Local mode is only trustworthy while it's exactly as strict as the database.

Since resolved — and a lesson in the tail

The spend cap was the one unproven thing here. It is now installed and tested against the live database: attempts 1–5 allowed with the counter climbing, 6 and 7 denied with reason = per_user. The global ceiling was proven separately and denies independently.

The first attempt to test it reported all seven attempts allowed and looked exactly like a broken cap. The test was wrong, not the code — seven lateral calls inside one SQL statement all read the same snapshot, which is nothing like seven HTTP requests. Worth remembering: a test that doesn't reproduce the real call pattern can condemn working code as readily as it can bless broken code.

Separately: that cap bounds calls, not dollars. A console spend cap is still a separate, necessary thing. Whether to set ANTHROPIC_API_KEY at all is still your call — I didn't touch it.

Housekeeping

The handoff docs were lying

HANDOFF.md is the file a fresh session starts from, and most of what it asserted had stopped being true: that the repo had never been pushed, that no accounts existed, that the app was in local mode. A cold-start brief that's wrong about the starting state is worse than none, so it's been corrected — along with two things a session arrives not knowing. It can reach Supabase and prove database guarantees directly, which is exactly what earlier work failed to do. And it cannot push, so claiming otherwise would be false.

Scars 6, 7 and 8 are written up. Scar 6 is the one worth reading twice: scar 5's diagnosis was right and its remedy was a silent no-op, and nothing caught it for months because the remedy was never executed against a database.

Nothing in Stage 4 was built — the fork-and-deploy wizard, sandbox automation, admin moderation, multi-currency. ROADMAP.md says not to until there are real sales and a request board to read, and building features nobody has asked for yet would have been the wrong use of the night.
